# 长任务编排架构

## 一、要解决的问题

LLM 处理长任务时存在**记忆衰减**：对话越长，早期关键信息越容易被压缩或丢失，
表现为任务中途丢失线索、重复已完成的工作、前后决策矛盾。

根因不是「模型不够聪明」，而是**把状态全押在上下文里**——
上下文是易失的、有界的、会被压缩的。任务越长，赌注越大。

## 二、核心思路：用空间换记忆

```
        传统做法                        本架构
   ┌──────────────┐            ┌──────────────┐
   │  单一长上下文  │            │   编排者      │
   │  状态全在里面  │            │  (只持有指针) │
   └──────────────┘            └───────┬──────┘
          ↓ 上下文膨胀                  │ 结构化交接
          ↓ 被迫压缩              ┌─────┴─────┐
          ↓ 信息丢失           ┌──┴──┐    ┌──┴──┐
       任务失败               │子任务│    │子任务│ ← 各自干净上下文
                             └─────┘    └─────┘
                                  ↓          ↓
                             ┌────────────────────┐
                             │  外部状态（磁盘/DB） │ ← 真正的记忆
                             └────────────────────┘
```

三条基本原则：

1. **状态外置**——关键事实写进文件/数据库，不依赖对话历史承载
2. **上下文隔离**——每个子任务用独立上下文执行，互不污染
3. **结构化交接**——子任务之间只传结论与指针，不传全文

## 三、角色分工

| 角色 | 职责 | 上下文特征 |
|------|------|-----------|
| **编排者 Orchestrator** | 拆解任务、派发子任务、汇总结果、判终止 | 短且稳定，只持有任务树 + 指针 |
| **执行者 Executor** | 在干净上下文里完成一个具体子任务 | 一次性，用完即弃 |
| **监督者 Supervisor** | 观察执行状态、判定异常、决定重启或收线 | 只读产出与日志，不介入业务 |

关键约束：**编排者绝不能亲自执行细节工作**。
一旦编排者开始贴长输出，它的上下文就开始衰减，全局视角随之丢失——
这是长任务系统最常见的自毁方式。

## 四、状态外置的约定

产出目录结构：

```
work/
├── findings.md        最终产出（人可读）
├── state.json         结构化状态（机可读）
├── agent.log          逐轮决策日志（可回放）
└── artifacts/         中间产物，按子任务分目录
```

**交接契约**：子任务结束时必须回报

```json
{
  "subtask_id": "s03",
  "status": "done | blocked | failed",
  "summary": "一句话结论",
  "artifacts": ["artifacts/s03/result.json"],
  "next_hint": "给下一个子任务的线索",
  "evidence_level": "L1-L4"
}
```

只传这个，**不传全文**。下一个子任务需要细节时，自己按路径去读。

## 五、上下文预算

经验值（按 128k 上下文模型估算）：

| 组成 | 预算 | 说明 |
|------|------|------|
| system + 任务书 | ~10% | 固定开销 |
| 近期对话 | ~40% | 保留最近 N 轮完整交互 |
| 工具输出 | ~30% | 单条截断到 6k 字符以内 |
| 余量 | ~20% | 突发输出与重试 |

超预算时的处理顺序：
1. 先截断工具输出（最占地方，信息密度最低）
2. 再压缩历史轮次（保留结论，丢弃过程）
3. 最后才缩减任务书（最关键，尽量不动）

**裁剪必须保持消息配对**：`assistant(tool_calls)` 与对应 `tool` 响应是一条链，
拆散会导致协议校验失败（详见 `docs/pitfalls.md`）。

## 六、终止条件

长任务必须有**明确的终止语义**，否则会无限空转或提前放弃：

| 信号 | 含义 | 动作 |
|------|------|------|
| `DONE` | 目标达成 | 落盘产出，正常结束 |
| `STOP` | 确认无法推进 | 落盘阶段性结论，交还人工 |
| `MAX_TURNS` | 预算耗尽 | 落盘进度，支持续跑 |
| `LLM_FAIL` | 环境/网关故障 | **不是任务穷尽**，修复后从 seed 续跑 |

⚠️ 最容易出错的是最后一条：把环境故障误判成任务完成。
判定前必须查日志里的真实错误（DNS 失败、超时、400 各有不同处置）。

## 七、续跑机制

长任务几乎不可能一次跑完，**续跑能力是必需品而非可选项**。

续跑的正确姿势：新开一个干净上下文，用一个 seed 文件恢复现场：

```markdown
# 续跑说明

## 已完成
- 子任务 s01-s03 完成，产出在 artifacts/s01..s03/
- 关键结论：<一句话>

## 当前进度
- s04 进行到 <步骤>，中间产物 artifacts/s04/partial.json

## 下一步
- 继续 s04 的 <具体动作>

## 已知约束
- <踩过的坑，避免重复>
```

这比"接着上一轮的完整对话继续"可靠得多：
后者会把上一轮的上下文膨胀原样带进来，很快再次触顶。

## 八、适用边界

**适合**：步骤数不确定、单步产出可能很长、需要多轮迭代探索的任务。

**不适合**：
- 步骤少于 5 步的简单任务（编排开销大于收益）
- 需要严格确定性的事务（LLM 决策引入不确定性）
- 实时性要求高的场景（每轮 LLM 调用有秒级延迟）
