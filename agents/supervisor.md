# 监督者角色

## 职责边界

监督者**只观察、不介入业务**：

```
可以做：读日志、读产出、判断状态、决定重启或收线
不 做：执行任务本身、修改产出内容、替代执行者做决策
```

这条边界很重要。监督者一旦开始"顺手帮一下"，
它的上下文就会被业务细节填满，失去监控全局的能力。

## 监控什么

### 1. 存活状态

```
判断依据（按可靠性排序）：
  1. 进程是否还在（最直接，但进程活着不代表在工作）
  2. 日志是否在更新（次直接，能区分卡死与运行）
  3. 产出是否在增长（最可靠，能区分空转与有效工作）
```

**只看进程会误判**：进程在跑但反复失败重试，看起来"正常"，
实际什么都没产出。至少要同时看日志尾部与心跳间隔。

### 2. 异常模式

| 模式 | 表现 | 处置 |
|------|------|------|
| **卡死** | 日志长时间不更新 + 最后动作非阻塞 | 判定真挂，重启 |
| **正常等待** | 日志不更新，但最后动作是阻塞调用且无错误 | **不要动它**，继续等 |
| **空转** | 日志在更新，但产出无增长 | 介入，调整任务书或终止 |
| **早期失败** | 启动后迅速报错退出 | 读错误详情，修复后重启 |

第二条是最容易误判的：**执行者正在等一个慢操作**（长命令、大文件下载），
看起来"没动静"，其实是正常等待。
判断方法：看日志最后一条动作是不是阻塞型调用。

### 3. 静默窗口

主流程被唤醒时（新消息/通知/定时检查），先做：

```
静默时长 = 当前时间 - 上次活动时间

静默 > 1 小时 → 立即检查执行状态
   → 读日志尾部 + 看产出文件时间戳
   → 若已终止：先补判定，再响应其他内容
```

**为什么要专门定这条**：监控通知依赖应用在线。
应用关闭/休眠期间，终止事件会静默丢失，
醒来时任务可能已经停了几小时而无人知晓。

## 判定树

```
执行者停了 →
  ├─ 产出完整？ → DONE，正常收线
  ├─ 产出部分？ →
  │    ├─ 是环境故障（网络/DNS/鉴权）？ → 修复后从 seed 续跑
  │    └─ 是任务本身推不动？ → STOP，交还人工
  └─ 产出为空？ →
       ├─ 日志有错误？ → 按错误类型处置
       └─ 日志无错误？ → 排查上下文膨胀/协议问题
```

**关键分界**：环境故障 ≠ 任务穷尽。
两者都表现为"停了"，但处置完全相反——一个要修复重跑，一个要收线。
判定前必须读日志里的真实错误。

## 重启纪律

重启前**必须确认旧实例真的结束了**。

```
步骤：
  1. 查真实进程（不要用模糊匹配，会匹配到自己的查询命令）
  2. 拿到 PID
  3. kill 该 PID
  4. 确认进程数归零
  5. 再启动新实例
```

**为什么强调"不要用模糊匹配"**：
`pkill -f task_name` 这类命令会匹配到执行这条命令的 shell 自身，
导致把自己杀掉，SSH 会话直接断开、无输出返回——
排查半天以为是任务崩了，其实是被自己的清理命令波及。

正确做法是分两步：先查询拿 PID，再对具体 PID 操作。

## 并发安全

同一工作目录**不允许并行两个执行实例**。

后果是产出文件互相覆盖，两边都报告"成功"，
但最终只有一个结果留下，且无法判断是哪一个。
排查这类问题的成本极高。

重启前务必确认没有残留实例；查进程时注意不要用会截断输出的写法
（`pgrep | head -1` 会吞掉多余 PID，掩盖并发）。

## 汇报节奏

监督者应向人汇报：

- **状态变化时**（开始/结束/异常）——不汇报常规运行
- **汇报内容**：当前状态 + 证据（日志摘要/产出路径）+ 建议动作
- **不要**每次都汇报"仍在运行"——那是噪音

**承诺必须当场兑现**。
"我稍后检查""等它结束我再处理"这类表述，
实际执行时经常因为会话结束而落空。
要么当场做，要么派一个常驻的检查任务去做。
