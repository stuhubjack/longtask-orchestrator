# 任务拆解与委派

## 核心原则

**拆解的目的不是"分得细"，而是"每个部分都能独立完成且结果可验证"。**

常见错误：

- 拆得**太细** → 编排开销大于执行成本，上下文全花在交接上
- 拆得**太粗** → 单个子任务自身就超上下文预算，问题没被解决
- 拆得**有依赖** → 子任务 A 的结论是 B 的前提，但 B 拿不到 A 的细节

## 拆解粒度

判据：**一个子任务应该在 5-15 轮工具调用内完成，产出可在 2k 字符内概括。**

| 信号 | 含义 | 动作 |
|------|------|------|
| 子任务需要 >20 轮 | 太粗 | 继续拆 |
| 子任务只需 1-2 轮 | 太细 | 合并到相邻任务 |
| 子任务产出无法一句话概括 | 太粗或目标不清 | 重新界定目标 |
| 子任务无法独立验证 | 目标模糊 | 补充验收标准 |

## 拆解方法

### 1. 先定终点，再倒推

从"完成时长什么样"出发：

```markdown
目标：产出 X（可验证的形态）
验收：看到 <具体产物> 即为完成
```

**验收标准必须可观测**。"尽可能多找问题"不是验收标准，
"确认项 ≥ 3 条且每条附可回放证据"才是。

### 2. 沿"能力边界"而非"步骤顺序"切分

按**需要不同能力/不同上下文**切，而不是按时间顺序切。

同样做三件事，两种切法：

```
❌ 按顺序切：步骤1 / 步骤2 / 步骤3
   → 每步都要重新建立全局认知，重复劳动

✅ 按能力切：广度扫描（需全局视角）/ 深度验证（需聚焦细节）/ 汇总产出（需全局视角）
   → 同类工作合并，上下文复用
```

### 3. 显式标注依赖

```json
{
  "id": "s03",
  "goal": "验证 s01 发现的候选点",
  "depends_on": ["s01"],
  "inputs": ["artifacts/s01/candidates.json"],
  "outputs": ["artifacts/s03/verified.json"],
  "acceptance": "每个候选点有明确结论（确认/排除/待验证）"
}
```

`inputs` 写**路径**不写内容——子任务自己去读。

## 委派契约

派发子任务时，**必须**提供：

```markdown
## 目标
<一句话，可验证>

## 上下文
<完成任务所需的最小背景>
<重要：子任务看不到你的对话历史>

## 输入
<文件路径，不是文件内容>

## 产出要求
- 写到：<路径>
- 格式：<结构>
- 必须包含：<必填字段>

## 验收标准
<怎样算完成>

## 约束
<不允许做什么 / 必须遵守什么>
```

**"子任务看不到你的对话历史"是最容易忽略的一条。**
编排者觉得"这个背景很明显"，但子任务是全新上下文，什么都不知道。
背景给少了，子任务会猜；猜错了，整条链就偏了。

## 交接回报

子任务结束时回报**结构化摘要**：

```json
{
  "subtask_id": "s03",
  "status": "done | blocked | failed",
  "summary": "一句话结论",
  "artifacts": ["artifacts/s03/result.json"],
  "next_hint": "下一步建议（给编排者的线索）",
  "evidence_level": "L1-L4",
  "blockers": ["如需人工介入的原因"]
}
```

**不传全文**。编排者只需要"发生了什么、东西在哪、下一步是什么"。

## 子任务独立性检查

派发前逐项自问：

- [ ] 这个子任务**目标可单句描述**吗？
- [ ] 它的产出**可独立验证**吗（不依赖子任务的"感觉"）？
- [ ] 所需输入**都在它自己能读到的路径**上吗？
- [ ] 它**不需要知道其他子任务的内部过程**吗？
- [ ] 如果它**失败**，我能判断出来吗？

有任何一项答"不确定"，就是拆解没到位。

## 编排者的自我约束

**编排者绝不能亲自执行细节工作。**

一旦编排者开始粘贴长输出、亲自跑命令做细节，
它的上下文就开始衰减，全局视角随之丢失——
这是长任务系统最常见的自毁方式。

编排者的职责严格限定为：

```
拆解 → 派发 → 收回报 → 判状态 → 决定下一步（继续/重派/收线）
```

看到子任务回报的结果有问题，**重新派一个子任务去处理**，
而不是"我顺手看一下"。

## 失败处理

| 子任务状态 | 处置 |
|-----------|------|
| `done` | 收回报，更新状态，派下一个 |
| `blocked` | 看 blockers：能解决的补上下文重派；不能的升级给人 |
| `failed` | **区分原因**：环境故障 → 修复后重派；能力不足 → 拆得更细 |

**重派前必须确认前一个真的结束了**。
同一子任务并发两份实例会导致产出互相覆盖，
这种错误很难排查（两边都"成功"了，但结果只有一个）。

## 终止与收线

编排者需要明确知道**什么时候停**：

- 验收标准达成 → `DONE`，产出汇总
- 预算耗尽 → 落盘进度，支持续跑
- 确认无法推进 → `STOP`，交还人工

**不要为了"显得有进展"而持续派发低价值子任务。**
长任务的价值在于达成目标，不在于轮次多。
